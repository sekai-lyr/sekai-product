# 性能与体验优化报告（第二轮）

承接 `BUGFIX_REPORT.md`（逻辑缺陷修复）。本轮做的是**可量化收益的优化**，
每项都已用脚本实测前后对比，并补了回归测试。

## 1. 首屏压缩：1,825 KB → 372 KB（-79.6%）

**问题**：登录页要加载 86 个未打包的 ES 模块 + 316 KB 未压缩 CSS，实测
**1,825 KB / 87 个请求**，且响应头里没有任何 `Content-Encoding`
（`application.yml` 未配置 `server.compression`，node 静态服务器也未做压缩）。
其中 `effects.js`(225 KB)、`engine.js`(139 KB)、`controller.js`(124 KB)、
animejs 的 draggable/layout(98 KB) 在登录页就全部下载，而它们只在决斗里用得上。

**改动**：
- `static/scripts/server.mjs`：新增 br/gzip 压缩（优先 br），带 120 条缓存，
  仅压缩文本类资源（图片不再二次处理），并补齐 `Content-Length` 与 `Vary`。
- `src/main/resources/application.yml`：开启 Spring 响应压缩
  （`server.compression.enabled: true`，列明 mime-types）。

**实测**（`.bug-review/measure-compression.mjs`）：

| | 未压缩 | 压缩后 |
|---|---|---|
| 首屏总字节 | 1,825 KB | **372 KB** |
| 请求数 | 87 | 87 |
| `engine.js` 单文件 | 143,012 B | **28,510 B**（br） |

## 2. 抽卡重复保护：120 包收集率 30.8% → 49.7%

**问题**：实测每包 8 张里第 1 包只有 3 张新卡，**第 30 包 0 张新卡**，
集齐 308 张按优惠券收集约需 221 包（221,000 决斗币）；而 AI 胜场 120 币/场、
50 关全通合计仅 85,125 币——集齐在数学上不可达，收藏进度几乎停滞。

**改动**：
- `js/packs.js` 新增 `applyDuplicateProtection(cards, pool, collection, rng)`：
  整包全为已拥有的卡时，把其中**稀有度最低**的一张换成尚未拥有的卡，
  优先同稀有度替换（不凭空抬高稀有度分布）。已集齐时原样返回。
- `js/app.js` 本地开包路径接入该函数（替换结果同样参与保底/统计计算）。
- `CollectionService.java` 服务端开包路径做同样处理（把 `ownedCounts` 的构建
  提前到抽卡之前，抽完判定"整批无新卡"后替换），并新增 `rarityRank` 辅助方法。

**实测**（`.bug-review/measure-duplicate-protection.mjs`，各开 120 包）：

| 包数 | 无保护累计收集 | 有保护累计收集 |
|---|---|---|
| 10 | 23 | 20 |
| 30 | 39 | 45 |
| 60 | 60 | 82 |
| 120 | 95（30.8%） | **153（49.7%）** |

「整包 0 张新卡」出现次数：**53 次 → 0 次**。

## 3. 起手重抽（mulligan）

**问题**：从真实卡池随机组 40 张卡组，平均只含 **6.4 张**免祭品怪兽却有
**17.3 张**需要祭品的怪兽；模拟 3,000 副卡组的 5 张开局手牌，**39.2% 只有
5 星以上怪兽**——空场时连盖放高星怪兽都做不到（盖放同样需要祭品），
等于白送一个回合。另有 4.2% 的起手完全无牌可出。

**改动**：
- `js/engine.js` 新增 `mulligan(player, handSize)`：手牌洗回卡组后按引擎随机源
  （PvP 下为共享种子）重新洗牌并抽满 5 张，保证可复现。
- `js/controller.js` 新增 `offerMulligan / autoMulliganAi / wantsMulligan`，
  在 `start()` 里于猜拳之前执行；AI 使用与玩家一致的判定规则
  （手牌没有 ≤4 星怪兽且没有魔法才重抽）。
- `js/ui.js` 新增起手手牌浮层（复用既有 discard 浮层样式，无新增 CSS）：
  展示 5 张手牌 + 「保留手牌 / 重抽一次」，并在无牌可出时给出建议文案。
- **联机对局不启用**：PvP 双方各自重抽会打乱共享种子的随机序列，需要协议级同步，
  这一点已写进规则页说明。
- 规则页新增第 20 条（起手重抽）与第 21 条（抽卡重复保护）。

## 4. 触屏提示修正

`js/ui.js` 的手牌 tooltip 原本写死"按住 Shift 拖放为里侧守备盖放"，
但代码里没有任何粗指针检测，手机上无法执行（点按菜单里其实有「里侧守备盖放」，
只是提示文案把人引到了做不到的操作上）。现按
`matchMedia("(pointer: coarse)")` 切换文案。

## 5. 卡图 WebP 管线：单张 430 KB → 21.5 KB

**问题**：卡池引用的 368 张原图合计 **154.5 MB**（单张平均 430 KB，最大 7.6 MB），
而渲染层一直取的是原图——`cardArtHtml` 的 `thumbnail || image` 分支因为插画表
`NIGHTCORD_ART` 是空对象，永远回落到全尺寸图。收藏页一屏 30 张就是 12.6 MB。

**改动**：
- 新增 `.bug-review/convert-card-images.py`（Pillow 12.3，实测支持 WebP 编码）：
  按**原相对路径**生成两档 WebP，不覆盖任何原始文件
  - `assets/cards/webp/thumb/...` 宽 320px q72 → 手牌、场上、收藏网格
  - `assets/cards/webp/card/...` 宽 640px q80 → 详情弹窗、卡包演出
- 新增 `js/card-images.js`：用纯路径约定做映射（不额外维护 368 条清单），
  给每张卡补 `thumbnail` / `fullImage` / `originalImage` 三个字段；
  已是 webp 的路径幂等，非 `assets/cards/` 的路径原样返回。
- `js/catalog.js` 在归一化之后套一层 `withCardImageSources`——这样所有渲染点
  （手牌、场上、收藏、卡组、卡包、详情）无需逐个改动就自动走缩略图。
- 卡片渲染统一带 `data-fallback-src`（原始图），`ui.js` 的图片兜底逻辑改为
  "WebP 失败 → 回退原图 → 再失败才显示占位"，即使某个 WebP 缺失画面也不会空。
- `index.html` 登录页的 3 张装饰卡图改用 thumb 档（原 551+363+143 KB → 49+17+25 KB）。

**实测**（`.bug-review/verify-card-images.mjs`，368/368 两档都存在、0 缺失）：

| | 原始 | thumb(320px) | card(640px) |
|---|---|---|---|
| 单张平均 | 430 KB | **21.5 KB** | 70.8 KB |
| 368 张合计 | 154.5 MB | **7.7 MB** | 25.4 MB |
| 收藏页一屏 30 张 | 12.6 MB | **644 KB** | — |

**首屏实测**（`measure-compression.mjs`）：

| | 改造前 | 现在 |
|---|---|---|
| 登录页总传输 | 约 2,882 KB（1,825 KB 未压缩 JS/CSS + 1,057 KB 装饰图） | **464 KB** |
| 其中装饰卡图 | 1,057 KB | 90 KB |

## 6. 资源瘦身：jar 1,136 MB → 266 MB

**发现**：`assets/cards` 下共 1,503 个文件、1,070.9 MB，但**只有 368 个文件
（146.2 MB）被卡池引用**。其中 `assets/cards/generated/` 一个目录就有
**307 张 PNG、873.8 MB**，而它仅被 `js/generated-art.js` 的
`GENERATED_ART_PATHS` 引用——该导出在整个代码库里**没有任何 import**，属纯存量。

**改动**：`pom.xml` 增加资源排除（`static/assets/cards/generated/**`），
只影响打包产物，源码目录里的原始文件一个都没删。

**实测**：`mvn -o -DskipTests clean package`

| | 之前 | 之后 |
|---|---|---|
| `target/classes` | 1,078.2 MB | 204.4 MB |
| `sekai-game-1.0.0.jar` | 1,136.4 MB | **266.5 MB** |

> 注意：必须用 `clean package`。直接 `package` 时 Maven 不会删除上一次构建
> 残留在 `target/classes` 里的排除文件，jar 依然是 1,136 MB。

# 第三轮：音效 / 局内反馈 / 陷阱连锁 / 工程基建

## 7. 程序化音效层（零素材）

**问题**：`assets/audio` 是空目录，全部前端代码里 **0 处**音频调用。而演出层有
23 万字符——动作很多却完全静音，是最容易被感知到的品质缺口。

**改动**：新增 `js/audio.js`，用 WebAudio **合成**音效（不需要任何音频文件）：
- 12 种音效：出牌、盖放、召唤、魔法、陷阱、攻击、伤害、破坏、揭晓、回合、胜利、失败、UI 点击
- 首次播放才懒创建 `AudioContext`（浏览器要求用户手势），`suspended` 时自动 resume
- 无 WebAudio 环境（Node 测试、老浏览器）下所有函数都是安全空操作
- 按稀有度变调（`pitchForRarity`：N 1.0 → UR 1.3），高稀有度的动作听起来更"重"
- 战斗音效分层：先出撞击音，再叠加"破坏"或"伤害"的结果音
- 开关的唯一来源是存档 `settings.soundEnabled`，设置页可关，启动时回放

## 8. 局内反馈三件套

| 功能 | 解决的问题 |
|---|---|
| **战斗预览** | 选中攻击者后，每个目标槽位直接显示"破坏 · 500 伤害 / 我方被破坏 · 受 500 点伤害 / 同值 · 无事发生"。`engine.predictBattle()` 是纯函数，测试用 12 个场景交叉校验"预览结论 == 实际结算"，逻辑漂移会立刻失败。 |
| **未完成动作提示** | 结束回合按钮旁显示"还可以召唤 1 只怪兽／还有可以攻击的怪兽／手牌还有 N 张可以发动"，按钮同时高亮。玩家不用逐张检查能不能出牌。 |
| **结束回合二次确认** | 还有可执行操作时弹确认框；没有待办动作时**不打扰**（零噪音）。 |

## 9. 陷阱连锁响应（能力已就绪，默认保守）

原实现用 `find()` 只取第一张盖放陷阱，"一次攻击只能有一张陷阱响应"。现改为按后场
顺序最多连锁 `BATTLE_RULES.maxResponseTraps` 张，减伤累加、任一无效化即终止连锁；
单张响应时行为与改造前完全一致。

**实测**：这一项对胜率格局基本无影响（限制 1 与限制 2 的统计逐位相同），因为多数
攻击响应陷阱会直接取消攻击，第二张通常没机会结算。因此保留了这项能力但不再激进调参。

## 10. 平衡实验室与 CI（本轮最重要的产出）

平衡实验室立刻暴露了一个严重问题。用同一套 AI 驱动、5 种构筑取向两两对战：

| 取向 | 卡组构成 | 胜率 |
|---|---|---|
| 曲线速攻 | 29 低星 / 1 高星 | 46.3% |
| 高星+祭品底子 | 14 低星 / 15 高星 | 53.8% |
| 魔法导向 | — | 56.3% |
| **陷阱导向** | 17 低星 + 20 陷阱 | **92.5%** |
| **纯高星（无祭品底子）** | 2 低星 / 33 高星 | **0.0%** |

先手胜率 51.8%（健康），但两端各有一个极端。继续做控制变量实验：

| 实验 | 陷阱取向胜率 | 结论 |
|---|---|---|
| 现状 | 92.5% | 畸形 |
| 每回合无效化上限 = 1 | 93.8% | 几乎无影响（消耗分散在各回合） |
| 每次无效化支付 300 / 500 / 800 LP | 91.7% / 90.8% / 86.7% | 影响有限 |
| **完全禁用攻击无效化** | **44.4%** | 决定性因素 |

**根因**：卡池 45 张陷阱里 **32 张带"这次攻击无效"**，而且无效化没有任何代价。
实测 842 次陷阱响应里 **842 次（100%）都取消了攻击**。攻击是主要取胜手段，
零代价的反复无效化直接把对手的进攻手段废掉。

**已尝试但回退的方案**（诚实记录）：
- 把 28 条陷阱配方改成"非无效化"效果 → 胜率反而 92.5%，且破坏了两个钉住真实卡
  行为的既有测试 → 按"改动让测试失败就是改动不对"的原则**已回退**。
- 每回合无效化上限 + LP 代价 → 破坏 3 个既有测试（它们钉住了"陷阱每张各响应一次"
  与"无效化不掉血"的既有设计）→ **默认值已改回中性**（0=不限制/免费），
  但保留为可配置项，随时可用实验室复测。

**建议**（需要卡牌设计决策，因此没有替你做）：把陷阱的"无效化攻击"占比降到 40% 左右，
或给无效化加真实代价（弃牌/献祭），然后 `npm run balance` 立刻能看到结果。

**CI 门禁**：新增 `.github/workflows/ci.yml`，每次提交跑
语法检查 → 290 条测试 → 120 局不变量压测 → AI 自战 → 平衡冒烟。
另新增 npm 脚本：`npm run check` / `test` / `fuzz` / `balance` / `selftest` / `verify`。

# 第四轮：新手教学（互动引导）

**问题**：游戏此前**完全没有教程**，规则页是 19 段纯文字，而规则深度接近游戏王
（祭品召唤、表示形式、陷阱时机、起手重抽…）。对完全没玩过的人，这是最大的流失点。

**设计原则**：
- **不新增一套规则引擎**：教学就是一局正常决斗，只是卡组、起手与提示被脚本固定住，
  所有操作都走真实引擎，学到的东西与实战完全一致。
- **卡组按条件从卡池里挑**（不写死卡 id）：选"4 星以下白板里攻击力最高的那只"作为
  教学怪兽、"攻击力 ≤1000"作为被攻击的假想怪，卡池调整后教学依然可用。
- **随时可跳过、不惩罚乱操作**：任何时候能点「跳过教学」；玩家做别的动作教练只会继续等。
- **入口不设门槛**：`#home-tutorial` 没有"卡组是否合法"的 disable 条件——新号零卡零卡组
  也能直接进教学（`createNewGame` 对 tutorial 模式跳过卡组校验）。

**教学流程（7 步 + 结束）**，顺序是按真实规则倒推出来的：

| 步骤 | 内容 | 推进条件 |
|---|---|---|
| 1 | 欢迎，认识起手手牌 | 点「下一步」 |
| 2 | 通常召唤（4 星以下免祭品） | 完成召唤 |
| 3 | 盖放陷阱（说明要过一回合才能发动） | 完成盖放 |
| 4 | 结束回合（**说明先攻首回合不能攻击**） | 完成结束回合 |
| 5 | 对手回合攻击 → **你盖的陷阱自动响应** | 陷阱实际发动 |
| 6 | 你的第 2 回合：**现在可以攻击** | 完成一次攻击 |
| 7 | 起手重抽 | 点「下一步」 |
| 8 | 教学结束 | 点「完成教学」 |

> 中途发现的一个设计事实：我最初把"攻击"排在第 2 步，结果被规则挡住——
> **先攻首回合不能攻击**（`GAME_STATE.firstTurn`）。把顺序改成"先召唤、再盖牌、
> 结束回合 → 对手回合演示陷阱 → 第二轮才教攻击"之后，不但走得通，还顺带把
> "首回合不能攻击"这条规则自然讲清楚了。

**稳定性细节**：
- 教学模式固定由玩家先攻，跳过猜拳与起手重抽浮层（重抽在第 7 步单独讲）。
- 教练面板默认 **穿透点击**（`pointer-events: none`，只有按钮可点），否则停在顶部会
  挡住对手的怪兽区——而第 6 步正需要点它。窄屏/矮屏自动移到下方。
- 教学不结算奖励、不计入战绩（`settleMatch` 对 tutorial 直接 return）。
- 第 5 步通过 `tutorial.forceAiAttack` 让 AI 跳过"亏怪就不打"的判断，保证陷阱一定被演示到。

**测试**：8 条，含一条**端到端**——用与 `main.js` 相同的路径搭一局教学，然后用真实引擎
依次完成召唤、盖放、结束回合、AI 进攻触发陷阱、第二轮攻击，断言教练在每一步都正确推进并
最终完成。

# 第五轮：陷阱卡池重做（把"堆陷阱就能赢"打下来）

**问题**：第四轮把平衡实验室做出来之后，它立刻指出"陷阱导向"构筑胜率 92.5%，而曲线卡组
只有 46%。审计整个卡池后，找到三个叠加的根因：

1. **84.4% 的陷阱都带"这次攻击无效"**（38/45），实测 842 次陷阱响应里 **842 次**都取消了攻击。
2. **隐式默认**：`themed-effects.js` 的 `themedAction` 用 `default:` 兜底，把**任何未实装行动**
   当成"这次攻击无效"。陷阱配方只写行动名，"是否无效攻击"不需要任何人表态——这才是占比
   失控的机制来源：新增一个行动，它默认就是全游戏最强的效果。
3. **分类与实现不同源**：引擎自己维护了一份"无效化行动"集合，实现却在另一份 switch 里。
   `sleep`/`freeze` 会把攻击者翻成守备，引擎随后按"攻击者已不能攻击"取消攻击，但它们
   没被算作无效化——"卡面没写无效、实际无效"的卡因此绕过了全部限制与统计。

**改动**：

| 改动 | 内容 |
|---|---|
| 单一真相 | `ATTACK_NEGATING_ACTIONS`（6 个明确写着"这次攻击无效"的行动）与 `ATTACK_FIZZLING_ACTIONS`（再加 sleep/freeze）由实现方导出，引擎不再自己维护一份 |
| 去掉隐式默认 | `default:` 改成显式列出 6 个无效化行动 + `default: return null`：未实装行动既不结算，也不会被当成无效化攻击 |
| 卡池重做 | 无效化陷阱占比 **84.4% → 26.7%**（12/45）。12 张无效化陷阱全部是 2 效果的 SR（让最朴素的卡承担最强的防守），14 张 SSR 与 5 张 UR 陷阱改成检索/回收/消耗/干扰身份 |
| 稀有度对称 | 陷阱与魔法一致：SSR/UR 的第一段效果支付 600/1000 LP，付不起就**不发动、也不消耗**那张卡 |
| 实验室 | 新增 `--trapmax=N`（构筑时限制陷阱张数）、按行动组合统计陷阱结算、取消率提示改为动态判断 |

**实测（同一实验室，每对 150 局）**：

| 指标 | 改动前 | 改动后 |
|---|---|---|
| 取消攻击占陷阱响应 | 100% | **11.9%** |
| 陷阱取向胜率 | 92.5% | **69.8%** |
| 真实对局胜率（扣掉对退化构筑的必胜局） | 78% | **59.8%** |
| 卡池无效化陷阱占比 | 84.4% | **26.7%** |
| 先手胜率 | 50.0% | 49.5% |

其他取向：混合 65.0% / 魔法 60.2% / 曲线 54.2% / 纯高星 0.0%。

**诚实记录两个测量结论**：

- `纯高星 0.0%` **不是 bug**：那份画像按定义只放 33 张 5 星以上、只留 2 张祭品底子，本来就
  召唤不出东西（5-6 星要 1 只祭品、7 星以上要 2 只）。它是故意造的"非法构筑"，作用是当标尺。
- 92.5% 里有相当一部分是**实验室画像差异**，不只是卡牌数据缺陷：陷阱画像只用 18 只怪兽
  （其余位置给陷阱），这 18 只全部取自"攻击力 + 效果数"排名的前列；曲线画像必须填满 29 只，
  把卡池里的孱弱怪兽也吃进来。于是做了陷阱张数控制实验（同一套画像，只改陷阱上限）：

  | 卡组里的陷阱张数 | 1 | 4 | 8 | 10 | 20 |
  |---|---|---|---|---|---|
  | 陷阱取向胜率 | 61.5% | 69.7% | 83.8% | 87.0% | 89.5% |

  陷阱密度确实是最强的单一杠杆，但**即使压到 8 张，数据不改依然是 78% 真实胜率**。
  所以两边都得动：卡牌数据本轮修完，密度实验工具留在实验室里（`--trapmax=`）。

**测试**：新增 4 条——无效化占比 ≤50% 且六种无效化行动仍有代表、非无效化陷阱不取消攻击
但效果照常结算、高稀有度陷阱付费与"付不起不消耗"、未实装行动不会被当成无效化攻击。

**还没做（需要卡牌设计决策）**：单张陷阱的"效果数"本身就是优势——一次免费响应结算 2-3 个
效果，等于凭空赚卡。真实对局胜率 59.8% 仍高于其他取向（46.9%~53.3%）。下一步要么把攻击响应
窗口限制为"只结算第一段效果"（需同步改卡面文字），要么给非无效化效果加发动条件。

# 第六轮：后场对策（给"无法回答的陷阱"补上答案）

**问题（审计发现）**：全游戏 **368 张卡里只有 2 张**能碰对手的后场（入门包里的「除魔」和
「陷阱拆除」）。也就是说：这张游戏里**盖下去的陷阱在规则上无法被回答**。第五轮把陷阱的
无效化占比压到 26.7% 之后，"堆陷阱"取向仍然有 59.8% 的真实对局胜率——根因不是陷阱数值，
而是对手根本没有处理它的手段。真实 TCG 里"拆后场"的卡正是为此存在的。

**改动**：

| 改动 | 内容 |
|---|---|
| 新增主题行动 | `disarm`（拆解）：破坏对方后场**最后一张盖放**的卡。明牌不算——避免把对手正在生效的卡也误伤。卡面文字照旧由 `ACTION_TEXT` 生成，不会出现文字与结算不一致 |
| 装到 6 张 SR 魔法上 | `picture_ex_003 / 006 / 010 / 108 / 113 / 115`。**刻意不放在 SSR/UR 上**：SSR 以上魔法发动要付 600/1000 LP，用它 1 换 1 去拆一张盖牌是亏的，那等于把一张高稀有度卡变成废卡 |
| AI 会用 | `cardValue` 现在认得"主题行动形式的拆后场"（原来只认数据型的 `destroySpellTrap`），并且当玩家后场有盖牌时把它当**紧急动作**优先执行（盖牌是未知威胁，比明牌更急） |
| 实验室 | 新增 `--spellmix=1`：默认按效果数排序的魔法画像只会拿 3 效果的 UR/SSR，2 效果的实用卡永远进不了卡组，等于**实验室看不到"后场对策"这条轴** |

**实测**：

| 指标 | 无后场对策 | 对手带拆除（`--spellmix=1`） |
|---|---|---|
| 陷阱取向胜率 | 69.8% | **63.7%** |
| 魔法取向胜率 | 60.2% | **70.5%** |
| 陷阱响应占攻击 | 16.9% | 13.4% |
| 最强取向 | 陷阱 | 魔法 |

也就是说：**陷阱从"最强"变成"第二"，前提是对手的卡组里真的带了答案**。只带一张拆除
（3 张同名）就足以改变格局，这是 1 换 1 应对手段该有的分量。

**诚实记录**：机制本身端到端可用（测试：先拆掉盖放的陷阱再攻击，这次攻击不再被无效、
伤害正常落地）；但它**不是一剂"平衡补丁"**——陷阱画像每回合都能补一张盖牌（卡组里 20 张），
对手的解只有 1 换 1，威胁数量始终大于解的数量。所以第六轮的定位是**补上缺失的玩家能动性**
（此前玩家对 AI 的盖牌完全无能为力），而不是把某个取向的胜率压到某个数字。

**测试**：新增 3 条——卡池必须至少有 6 张能拆后场且不自带 LP 费用（防止"无法回答"再次回归）、
拆解端到端可用、拆解只对盖放的卡满足发动条件。

# 第七轮：魔法卡代价重做（面向大众可玩性）

**问题（审计发现）**：全卡池 105 张魔法里，所有"带代价"的 7 张 UR 收的都是同一种
代价——**随机丢弃 1 张手牌**（`authored-card-rules.js` 按"稀有度 + 行动名单"统一发放）。
这有三个叠加的可玩性问题：

1. **不可控**：丢哪张由引擎随机决定，玩家完全无法计划；「杖与剑的契约」甚至可能
   把你想召唤的那张怪兽丢掉——这是最劝退新人的一种代价。
2. **双重损失**：发动魔法本身已经消耗一张手牌，再弃一张是 -2 张卡换一段效果。
   对还没建立"卡差"概念的新玩家，等于"抽到 UR 也不敢用"。
3. **千卡一面**：7 张不同主题的卡（归还/爆破/盖放/登场）付一模一样的代价，
   高稀有度卡失去了设计个性。

审计还发现一个隐藏缺陷：`activateSpell` 先把魔法从手牌移出、再支付弃牌代价；
当手牌恰好只有这一张时，"干跑校验"通过、支付时手牌已空——`hand.splice` 取到
`undefined` 并被静默塞进墓地（数据损坏，回忆类效果之后可能拿到 undefined）。

**设计原则（本轮）**：

| 原则 | 落地 |
|---|---|
| 默认免费 | 施放魔法已经亏一张牌，绝大多数魔法保持零代价 |
| 收费只收可预期的税 | 需要限制的禁术一律改收 LP，金额按效果强度分档（300/500/600/800），不再随机弃牌 |
| 付不起不惩罚 | LP 不足时既不发动、也不消耗这张卡，卡留在手里 |
| 卡面即结算 | 代价金额写进卡面文字；发动消息回传"支付500LP"，LP 为什么少了一目了然 |
| 1 换 1 的功能解零代价 | 拆后场等实用魔法保持免费（既有测试继续钉住） |

**改动**：

| 文件 | 内容 |
|---|---|
| `js/authored-card-rules.js` | `authoredEffectCost` 重写：魔法默认免费，仅 4 张禁术保留 LP 代价——碎穹 500 / 寄往遥远彼岸的信 300 / 心印同框·八千年的契约 600 / 异世残绪 800；八千年的思念、月下传讯、杖与剑的契约改为免费；陷阱不再自动征收弃牌 |
| `js/engine.js` | `_checkCost` 支持排除"发动中的卡"自身、支付前二次校验数量（修掉 undefined 进墓）；`canPlayEffect` / `canActivateSetSpell` / `activateSpell` 改用类型安全的代价校验并回传准确原因；新增 `describeCost` 统一"支付XLP／丢弃X张"文案；发动消息、陷阱结算、怪兽主动技日志都带上代价 |
| `js/app.js` | 规则页第 05 条补充"大部分魔法无需代价；付不起不发动、不消耗" |
| `test/spell-cost-accessibility.test.js` | 新增 8 条代价可玩性测试（见下） |

**结果**：带代价魔法 **7 张（清一色弃牌）→ 4 张（LP 四档）**，其余 101 张全部免费；
全卡池魔法代价中不再存在随机弃牌。

**实测**（`node scripts/self-play-balance.mjs 40`，同一卡池与随机种子前后对比）：

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 魔法取向胜率 | 69.4% | 71.3% |
| 陷阱取向胜率 | 62.5% | 63.1% |
| 曲线取向胜率 | 66.3% | 65.6% |
| 混合取向胜率 | 51.9% | 50.0% |
| 先手胜率 | 50.5% | 51.0% |
| 平均回合数 | 9.7 | 9.6 |

魔法取向小幅上升（关键 UR 不再随机丢牌后才敢稳定使用），先后手与平均回合数不变，
没有出现新的失衡取向。

**测试**：新增 8 条——卡池魔法零随机弃牌、带代价魔法必须是 ≤800 的 LP 且至少 3 档、
≥90% 魔法免费、卡面文字与代价一致、LP 不足不发动不消耗、LP 真实扣除并写进发动消息、
盖放发动走同一条代价规则、弃牌代价回归（不能丢掉发动中的卡自己、墓地不出现 undefined）。

**验证**：`npm run check` 通过；`node --test test/*.test.js` **375 通过 / 0 失败**
（改造前基线 367 通过 / 0 失败）；`src/test/js` 保持 37/39（2 条为既有卡面文案重复，
与代价无关）；不变量压测 120 局 0 异常；AI 自战 20 局全部正常结束。

# 第八轮：卡背重做（把「字母 + 蓝方块」换成一张真卡）

**问题**：卡背此前是 CSS 画的「深空底 + 六属性极光环 + 斜向网格 + SVG 徽记」，
而承载它的容器各自还叠了一层自己的装饰——卡组堆是青色斜纹底 + 2px 青边、
墓地堆是橙色斜纹底 + 2px 橙边、里侧盖牌是 2px 青边，每个容器又在卡背上扣了一个
`inset` 白框。层数一多，在 64×88 的卡组堆上就只剩几块色斑和一条白框，
"不像一张卡"。

**改动**：

| 文件 | 内容 |
|---|---|
| `static/assets/cardbacks/source/sekai-card-back-master.png` | 新卡背母图（658×892，白底金色镂空边框 + 蓝色晶核） |
| `SekaiGame/scripts/build-card-back.py` | 构建脚本：连通域泛洪判白底（**画框内**的星芒高光保留，**画框外**的碎块与灰线稿清掉）→ 换成与主题同源的深空底 → 按 0.70 画布留白居中 → 输出 WebP |
| `static/assets/cardbacks/sekai-card-back.webp` | 产物 563×804，**71 KB**（母图 881 KB，↓ 92%） |
| `static/js/card-view.js` | `sekaiCardBackHtml` 删掉整段 SVG 徽记，改为纯容器 + 虹彩层 + 底部标签 |
| `static/css/style.css` | `.sekai-card-back` 改为真实立绘；删掉 `::before` 极光环与斜纹网格；卡组 / 墓地 / 手牌 / 卡序列表 / 里侧盖牌容器统一撤掉自画底纹与 `inset` 白框（卡组与墓地仍用冷/暖边框微差区分） |
| `SekaiGame/pom.xml` | 母图不进 jar（`static/assets/cardbacks/source/**`） |

**为什么画布定在 0.70、而不是立绘本身的 0.7377**：卡背在各处被拉伸的宽高比并不一样
（场地卡 100×130 = 0.769 最宽，卡包预览 0.7 最窄）。CSS 用 `cover` 填充，元素比图宽
就上下裁、比图窄就左右裁。把画布定在最窄的 0.70、并让立绘只占画布高度 89%，
两个方向的裁切量（最坏 36 px）都落在留白里。脚本每次生成都会自己报校验：

```text
画布      : 563×804  (比例 0.700)  立绘 528×716 居中，留白 横向 17px / 纵向 44px
裁切校验  : 场地卡 100×130 用掉留白的 82%✔  卡组堆 64×88 用掉留白的 34%✔
            对手手牌 58×80 用掉留白的 31%✔  卡包预览 .70 用掉留白的 1%✔
```

> 踩到的坑：**只做纵向留白是无效的**。画布越高，`cover` 裁掉的也越多，而且两侧
> 裁切量恒比留白多出 15.4 px（就是立绘宽度等于画布宽度时，它比 0.769 那个框高出来的
> 那 30.8 px 的一半）。必须让立绘在画布上**横向也缩一点**，才能真正裁不到画框。

**验证**：`node --test test/*.test.js` **387 通过 / 0 失败**。
`static/test/cardback-preview.html` 用真实样式表 + 真实容器结构渲染全部 7 个出现位置
（里侧盖牌 / 卡组堆 / 墓地堆 / 对手手牌 / 卡序列表背面 / 卡包翻面 / 268px 启动演出），
截图见 `.bug-review/cardback-preview.png`；无头 Edge 2x 渲染确认画框在任何比例下都没被切到。
