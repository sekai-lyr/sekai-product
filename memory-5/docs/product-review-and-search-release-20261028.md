# 前后端改进建议与搜索更新记录

日期：2026-10-28（北京时间）

范围：结合线上登录页、现有页面和后端代码提出建议；落实小范围高价值改动并同步部署。保留现有四套主题和播放演出，不改动其他未提交工作。

## 已上线：搜索体验

- 支持全部／歌曲／歌单筛选，显示分类数量与结果总数。
- 每页显示 20 条结果，翻页保留关键词和类型；越界页码自动收敛到有效范围。
- 区分首次进入、无匹配结果和关键词超过 160 字符，提供可执行的下一步提示。
- 空白、超长关键词不读取歌库；大小写匹配使用固定 Locale，避免服务器语言配置影响结果。
- 搜索框有明确标签、移动端输入提示和键盘焦点；结果列表复用现有主题色，长文字可换行。
- 保持登录保护和当前账号的数据范围。

性能边界：本次分页限制页面输出数量；有效搜索仍读取当前账号歌库和歌单，在内存筛选。没有将其描述为数据库分页或大歌库性能问题已经解决。

## 建议优先级

| 优先级 | 方向 | 具体建议及依据 | 验收方式 |
| --- | --- | --- | --- |
| P1 | 前端：首次使用 | 首页“添加歌曲”目前跳到歌曲库；建议空歌库时直接突出“导入本地音视频”，解释信息导入与本机文件关联的区别，减少新用户找不到可播放音频的问题。 | 新账号从首页可以明确完成关联文件、创建歌单、开始播放。 |
| P1 | 前后端：首页信息准确性 | `PageControl.home` 的“最近歌曲”来自歌库前六项；“常听作品”来自歌库作品数量统计。建议先改成准确的“最近入库／收藏最多的作品”等文案（需先核对实际排序与口径），或使用已有收听记录提供真正的最近播放及常听统计。 | 展示顺序与定义一致；跨账号隔离；无播放记录时显示明确空状态。 |
| P1 | 后端：搜索查询 | 随歌库规模增长，将账号范围、关键词匹配、类型和分页下推到查询层，仅读取展示所需字段；先测量耗时再决定索引方案。当前实现仍加载完整歌曲对象。 | 使用大歌库数据测查询耗时、内存及响应大小；分类计数和翻页结果保持一致。 |
| P2 | 后端：歌单批量读取 | `LocalLibraryControl.list` 对每张歌单单独查询歌曲，形成随歌单数量增长的查询次数。建议按账号一次批量取得歌单歌曲关系，再组装响应。 | 多歌单情况下查询次数保持固定；不同账号数据不能混入。 |
| P2 | 前端：播放器操作层级 | 保留播放器的演出特色，把播放、进度、队列作为第一层；演出选择、均衡器和高级选项按任务分组，减少初次进入时的选择负担。此项为源码层建议，本次未完成已登录线上播放器的完整视觉验收。 | 手机单手完成播放与切歌；高级功能仍可发现；键盘和触控均可操作。 |
| P2 | 后端：长任务状态 | 对实测耗时的导入／媒体分析增加进度、失败原因和可重试任务；不要将请求结束后失效的 MultipartFile 直接交给后台线程。避免未经测量先引入 Redis 等额外组件。 | 大文件不会阻塞页面；重试不会产生重复歌曲；任务状态只对所属账号可见。 |
